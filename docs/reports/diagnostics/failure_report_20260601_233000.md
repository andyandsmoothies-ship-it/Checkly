# Failure Report: Checkly API Executable Lock Failure

## Input Lineage

- **Bug/Error Context**: Output from running `dotnet run` inside the `C:\Users\HP\Documents\GitHub\Checkly\server` directory.
- **Source Log Path**: Console error logs showing locked process `Checkly.Api (38240)`.

## Root Cause

An instance of `Checkly.Api.exe` (PID `38240`) from a previous run or debugging session is still active in the background. Because it is running, the Windows OS maintains an exclusive read/write execution lock on the binary:
`C:\Users\HP\Documents\GitHub\Checkly\server\bin\Debug\net10.0\Checkly.Api.exe`

When the user attempts a new `dotnet run` or `dotnet build`, MSBuild compiles the code into `obj\Debug\net10.0\apphost.exe` and tries to copy it to the destination path. The copy operation fails with error `MSB3021` because the target executable file is locked.

## Explicit System/Code Trace

1. **Premise 1**: Operating system processes keep open file handles on their primary executables during execution.
2. **Premise 2**: Windows strictly prohibits overwriting or deleting files that have active execution handles.
3. **Premise 3**: MSBuild target `Copy` in `Microsoft.Common.CurrentVersion.targets` at line 5381 tries to overwrite `bin\Debug\net10.0\Checkly.Api.exe`.
4. **Proof**: 
   - We executed `tasklist /FI "IMAGENAME eq Checkly.Api.exe"` to query active background tasks.
   - Result:
     ```
     Image Name                     PID Session Name        Session#    Mem Usage
     ========================= ======== ================ =========== ============
     Checkly.Api.exe              38240 Console                    1     96,124 K
     ```
   - This proves process `38240` is running and is the source of the file lock.

## Proposed Scope-Limited Fix

The fix consists of forcefully terminating the running zombie/background instance of the API process using Windows native tools to release the file lock.

### Proposed Command
```cmd
cmd /c taskkill /F /IM Checkly.Api.exe
```

### Trade-offs / Pros & Cons

- **Pros**:
  - Immediately releases the file handle/lock.
  - Allows MSBuild and `dotnet build` to succeed instantly without needing a system reboot.
  - Safe and isolated scope with zero impact on source code or databases.
- **Cons**:
  - Any unsaved telemetry or logs in memory for that specific running process will be lost (acceptable since it is a development server instance).
