### What can we realistically answer for the BOD?
The existing DB has:
- Submissions (audits) with TotalScore, CompletedAt, StoreId, AuditorId
- ActionPlans with CriteriaLabel, Status, CreatedAt, ClosedAt, StoreId
- Stores with Name, Province, District
- Categories (as part of the audit template/criteria structure)

Questions the BOD CAN ask that we CAN answer:
1. "Which stores have worst [Category] compliance?" → Query Submissions + CategoryScores
2. "Show me the open action plans for [90+ days] bucket" → EXISTS on server, not wired on client
3. "Tell me more about the bottom store: recent audits, category breakdown" → Query Submissions by StoreId
4. "What's the auditor bias breakdown?" → Exists on live endpoint, not surfaced in UI
5. "Which month had the dip?" → Trend data exists; add tap to select a month

Questions the BOD asks that we CANNOT answer (data gap):
- "What's the root cause of the failure?" (No root cause field in DB)
- "What did the auditor comment on this?" (Comment data not aggregated in BOD level)
- "Show me the photo evidence" (Photos exist but beyond analytics scope)

### Pattern Identification
**System Design Pattern:** `Modal Overlay Drill-Down` (not a new page navigation)
- Each card tap opens a modal bottom sheet or an expanded inline section
- This avoids navigation complexity (GoRouter ShellRoute issues from GEMINI.md Gotcha 15)
- All data fetched on-demand when the sheet opens (lazy loading)
- This is the same pattern already used by BodStoreSyncModal and BodApBucketDetailSheet

### Architecture Options

**Option A — Strict Native Fit (Minimum viable, no new endpoints)**
- Fix the wiring gap in Card 5 (AP drill-down) by adding `getApBucketDetail()` to API service
- Fix Card 3 (Store leaderboard) by enriching BodStoreSyncModal with category scores from existing snapshot
- Show BiasRating in Card 6 by adding field to snapshot DTO (BodAuditorProductivity)
- Leave Cards 1, 2, 4 with no tap (not enough data to drive a useful modal)
- Risk: BOD still can't drill into Category Weakness or Trend. Admin still stumped on some questions.

**Option B — Pragmatic Balance (3 new server endpoints + 3 new modals)**
- Fix Card 5 wiring (existing endpoint, just add client method)
- Fix Card 6 BiasRating gap (add to snapshot DTO + show in widget)
- Add Card 4 (CategoryWeakness) drill-down: NEW endpoint `GET /analytics/bod/category/{categoryName}` returns stores sorted by that category score
- Enrich Card 3 (StoreLeaderboard) modal: NEW endpoint `GET /analytics/stores/{storeId}/bod-summary` returns last 3 audits + category breakdown for a store
- Add Card 1 (KpiGrid) drill-down: Tap on "Open APs" → reuse existing AP funnel bottom sheet with no filter (shows all open). Tap on "Avg Score" → show regional score comparison.
- Leave Card 2 (ScoreTrend) no tap (trend month breakdown requires complex schema not yet supported)
- This is the best balance: 2 new backend handlers, 2 new Flutter sheets, fixes 2 gaps. Answers 80% of likely BOD questions.

**Option C — Enterprise Textbook Overhaul (Universal Drill-Down Engine)**
- Create a generic `BodDrillDownService` that accepts a drill-down type enum
- Add dedicated analytics DB views for per-store, per-category, per-auditor queries
- Add full navigation to dedicated sub-pages per drill-down topic
- Add time-range selector to every drill-down
- Risk: Massive scope. Weeks of work. YAGNI applies. The BOD meeting is happening now.

### Blind Spots
1. **BiasRating in Snapshot vs Live**: The snapshot DTO (`BodAuditorProductivity`) does not have `BiasRating`. Even if we add it to the Flutter widget, the NIGHTLY SNAPSHOT route will never show it unless we also update `BodReportCalculator.cs` (418-line monolith, declared OUT OF SCOPE). Option B must use the LIVE auditor endpoint for the drill-down modal instead.

2. **Category Weakness data shape**: `BodCategoryWeakness` in server DTOs has: `CategoryName`, `TemplateTitle`, `AvgScore`, `AuditCount` — but NO list of stores that failed. A new endpoint must JOIN submissions+categories to return per-store breakdown for a given category. This query may be slow without a composite index on `(template_item_id, store_id)`.

3. **Store BOD Summary modal vs NavigateToStore**: The store summary modal (Card 3 enrichment) will duplicate logic already available on the Store Detail page. If the admin navigates to Store Detail instead, they get full history. But the BOD presentation context means leaving the analytics page is bad UX (they lose their filtered state). The modal must be self-contained and NOT navigate away.

### Server Changes (2 New Handlers)

**S1: `GetStoreBodSummary.cs`** — `GET /analytics/stores/{storeId}/bod-summary`
- Returns: last 5 audits (date, score, auditor), top 3 failing categories for this store
- Joins: `Submissions` + store filter, group by template_section or category
- Guard: `RequireCapability(AppCapabilities.AnalyticsBod)`

**S2: `GetCategoryDetail.cs`** — `GET /analytics/bod/category/{categoryName}`  
- **Crucial Rule (Terminology Map)**: In the UI, users see the word "Audit". In the database and server code, the entity is named `Submission`. The builder must query the `Submissions` table, not an "Audits" table.
- **Database Query Optimization (Category Weakness)**: To query the worst stores for a specific category very fast, **do not join** the `Stores` table. Instead, query the `SubmissionSectionScores` table directly and read the denormalized `StoreName` field from its parent `Submission` entity. Always add `.AsNoTracking()` to keep memory usage low.
- **Data Flow Diagram**:
  ```text
  [UI (Taps Category)] ──► [GET /analytics/bod/category/{name}] 
                                         │
                                         ▼
                           [SubmissionSectionScores]
                                         │ (Reads denormalized StoreName)
                                         ▼
                           [StoreName, AvgScore, Count] ──► [UI List Sheet]
  ```
- Returns: `List<CategoryStoreEntry>` with `{ StoreName, AvgScore, AuditCount, FailureCount }` sorted by AvgScore ASC (worst first)
- Guard: `RequireCapability(AppCapabilities.AnalyticsBod)`

## 3 Blind Spots (NFR Analysis)

1. **Query Performance on Category Breakdown**: `GetCategoryDetail` must JOIN submissions → criteria → filter by category label string match. Without a `GIN` index on criteria label or a pre-aggregated view, this may be slow for chains with 10k+ audit records. Must add `.Take(50)` cap and `AsNoTracking()`. **Mitigation:** Add `IMemoryCache` TTL=120s keyed by `categoryName`.

2. **Snapshot vs Live Data Mismatch**: The main report comes from a nightly SNAPSHOT. The drill-down sheets fetch LIVE data. If the BOD asks about a store shown in last night's snapshot, the drill-down sheet may show today's live data (which could be slightly different). The admin must be warned via a subtle note in the sheet header: `"Live data as of [now]"`. This is intentional UX, not a bug.

3. **Modal Max Height on Tablet**: `showModalBottomSheet` with `isScrollControlled: true` may expand to full screen height on tablet if a store has many audits in `BodStoreDetailSheet`. Must apply `maxHeight: MediaQuery.of(context).size.height * 0.85` constraint on the container to prevent the sheet from covering the entire dashboard.

### Anti-Silent Failure in Integration Tests (Mandatory Rule)
When the builder writes integration tests for the two new endpoints (`GetStoreBodSummary` and `GetCategoryDetail`), they **MUST NOT** assert a raw boolean success code like `Assert.True(response.IsSuccessStatusCode)`.
They must explicitly read and print the actual HTTP response body on failure so that SQL, schema, or authorization errors are immediately visible in the test execution logs.
Example pattern:
```csharp
if (!res.IsSuccessStatusCode)
{
    var body = await res.Content.ReadAsStringAsync();
    Assert.Fail($"HTTP {res.StatusCode}: {body}");
}
```
