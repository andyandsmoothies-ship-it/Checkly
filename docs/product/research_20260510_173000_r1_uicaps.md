# Research: Proactive UI PBAC Capability Prevention

## [ORIGIN_IDEA]
I observed that backend permission blocks (403 errors) create bad UX when a user clicks a button they shouldn't have access to. The UI needs to be "dumb" and strictly read PBAC capabilities to proactively hide/show controls, preventing unauthorized actions at the UI level before the backend ever rejects them.

<latent_space_scratchpad>
**Problem Diagnosis:**
- Currently, users can see UI controls (buttons, links, form inputs) for actions they are not authorized to perform.
- When they interact with these controls, the backend properly enforces PBAC (returning 403 Forbidden).
- However, this results in a poor user experience (UX) because the user is reacting to a failure rather than being guided by a tailored UI.

**System Assessment:**
- Flutter App currently uses `AuthManager` which holds a `Set<String> capabilities` (the active user's permissions loaded from Drift).
- We also already have `PolicyManager` for routing logic and `PermissionGuard` (in `lib/_shared/widgets/permission_guard.dart`) for conditional widget rendering.
- The gap isn't infrastructure; the gap is enforcement across all actionable components. Many screens either don't use `PermissionGuard` or still rely on role-based strings.

**E2E Map Integration:**
- Backend Trigger: `GET /api/auth/capabilities` or similar sync endpoint populates the user's capabilities.
- Local Storage: Drift caches capabilities in SQLite for offline support.
- State Manager: `AuthManager.capabilities` (ValueNotifier/Listenable) broadcasts changes.
- UI Layer: Widgets wrapped in `PermissionGuard` react instantly, showing/hiding based on presence of specific capabilities (e.g., `AppCapabilities.templatesCreate`).

**Architectural Tradeoffs & Blind Spots:**
1. **Layout Shifting (CLS):** If we conditionally remove large UI blocks rather than disabling them, the page layout might jump. (Blind Spot 1: Visual stability).
2. **Offline Staleness:** If a user is demoted but remains offline, the local cache still grants them access. The UI will show the button, they will click it, and if it's an offline action, it might queue, or if online, it hits a 403. The backend guard remains the ultimate source of truth. (Blind Spot 2: Eventual consistency in offline scenarios).
3. **Discoverability vs Security:** Hiding buttons entirely (security) vs disabling them with a tooltip (discoverability). A strict "dumb" UI hides them, which is cleaner but users might wonder where a feature went. (Blind Spot 3: UX communication of missing rights).

**Conflicts with Rules:**
- We MUST use the existing `PermissionGuard` and `AppCapabilities` constants instead of hardcoded strings (Rule: No Magic Strings).
- We MUST not refactor the entire state management (Rule: Use Existing Tools).
</latent_space_scratchpad>

## E2E Workflow Map

1. **Backend Capability Sync** (Status Quo)
   ASP.NET PBAC Engine -> `/api/system/capabilities` -> Flutter `PolicyApiService`
2. **Local Memory Update** (Status Quo)
   `PolicyApiService` -> Drift DB -> `AuthManager.capabilities` (ValueNotifier)
3. **UI Rendering** (Target State)
   Flutter Widget Build -> `PermissionGuard` -> Checks `AuthManager` -> Hides/Shows Widget
4. **Action Execution** (Protected)
   Widget (only if visible) -> Manager -> API -> 200 OK

### Context Handoff Points
- The UI relies *exclusively* on `AuthManager.capabilities`. The UI does not compute roles.
- `PermissionGuard` handles the widget-level handoff.
- The Router (AppRouter) handles the page-level handoff.

## Impact Spectrum

| Option | Approach | Pros | Cons |
|---|---|---|---|
| **(A) Strict native fit (PermissionGuard Wrapping)** | Wrap every protected action button (FAB, menu items) in `PermissionGuard` utilizing existing `AppCapabilities` constants. | Reuses existing Checkly infrastructure. Zero new dependencies. High cohesion. | Requires manual auditing of all screens to apply the wrapper. |
| **(B) Pragmatic balance (Role-Based Display)** | Hardcode role checks in UI (e.g., `if (user.role == 'admin') showButton()`). | Fast to implement for known roles. | **CONFLICTS with PBAC architecture.** Breaks dynamically assigned capabilities and creates split-brain logic. |
| **(C) Enterprise textbook overhaul (Server-Driven UI)** | Backend returns a JSON layout defining exactly what buttons to render on screen. | UI is truly "dumb". Maximum security. | Violates Checkly's offline-first architecture. Unnecessary complexity. |
