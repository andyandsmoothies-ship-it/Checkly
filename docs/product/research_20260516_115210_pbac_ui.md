# [ORIGIN_IDEA]
Evaluate PBAC (Policy-Based Access Control) UI capability mapping for enterprise-grade consistency, preferring strong structural limits over maximum flexibility when deciding between showing/hiding UI elements vs relying on capabilities.

<latent_space_scratchpad>
Debating Tradeoffs:
Currently, the codebase uses two conflicting paradigms for showing/hiding UI elements:
1. `PolicyManager`: Native Flutter capability check (e.g., `_di<PolicyManager>().can('programs:list')`).
2. `ActionGuard` (HATEOAS): Backend computes business rules + PBAC into an `allowedActions` array. The UI blindly obeys this array.

Enterprise systems fail when business rules are duplicated across the frontend and backend. If we use `PolicyManager` to show/hide a "Submit Evidence" button, the frontend must ALSO check if the item's status is 'open' (because you can't submit to a closed plan). This duplicates state logic: `if (status == 'open' && policy.can(write))`. 

If we use HATEOAS, the backend computes the capability AND the state, and simply says `allowedActions: ["submit_evidence"]`. The UI is dumb, structural, and perfectly safe. 

However, for Global Navigation (like Tabs and Routes), HATEOAS fails because there is no "item" to pull `allowedActions` from. For this, `PolicyManager` is the only viable tool.

Verdict: We must enforce a strict binary boundary.
- Global Structural UI = PolicyManager.
- Item-level Contextual UI = ActionGuard (HATEOAS).
</latent_space_scratchpad>

## E2E Workflow Map (Hybrid PBAC)

```ascii
[Global Nav & Routing]
JWT Capabilities --> PolicyManager --> MainShell Tab Visibility
                                   --> Router Guards
                                   --> Global "Create New" FABs

[Contextual Actions (Items/Details)]
Backend Entity + JWT --> DTO `allowedActions: ["edit", "delete"]`
                     --> Flutter Model `allowedActions`
                     --> UI `ActionGuard` wraps the Edit/Delete Buttons
```

## Impact Spectrum

| Strategy | Architecture | Pros | Cons |
|---|---|---|---|
| **A: Strict Hybrid (Recommended)** | `PolicyManager` for Global Nav.<br>`ActionGuard` for Item actions. | Zero business logic duplicated on frontend. Enterprise safe. | Requires Backend to compute `allowedActions` for every DTO. |
| **B: Frontend Heavy** | `PolicyManager` everywhere. | Flutter controls everything natively. | UI must constantly check entity `status` alongside capability. High risk of UI/Policy drift. |
| **C: Pure HATEOAS** | Backend controls all navigation and action buttons dynamically. | Ultimate security. | Sluggish UX, requires constant API polling, poor offline support. |

## UI Component Routing Table & PBAC Rules

| UI Component Type | Mechanism | Justification |
|---|---|---|
| **Bottom Tabs** | `PolicyManager` | Global access. No contextual entity exists yet. |
| **Router Paths** | `PolicyManager` | Prevents deep-linking bypasses. |
| **Global "Create" FAB** | `PolicyManager` | Global action. E.g., "Create Audit" isn't tied to an existing audit. |
| **List Items (Cards)** | `ActionGuard` | Contextual. Item might be locked, archived, or user might lack permission. |
| **Detail Pages (Buttons)** | `ActionGuard` | Contextual. Eliminates complex `if (status == X && role == Y)` checks in UI code. |

## Blind Spots & NFRs
1. **Payload Bloat**: Returning `allowedActions` strings on massive paginated lists (e.g., 1000 items) could bloat the JSON payload.
2. **Offline Mode**: If the app is fully offline and the user creates a local entity, the backend hasn't computed `allowedActions` yet. The UI needs a local fallback projection mechanism.
3. **Cache Invalidation**: If PBAC permissions change mid-session, cached DTOs with old `allowedActions` arrays will show buttons that now yield 403 Forbidden errors when tapped.
