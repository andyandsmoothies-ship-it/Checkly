# Research: Empathetic Error Messaging UX

## [ORIGIN_IDEA]
The user wants to apply good error messaging into the system. Messages should explain what happened and why, provide reassurance, be empathetic, help the user fix the issue, and give them a way out (e.g. an actionable next step).

<latent_space_scratchpad>
**Status Quo Audit:**
- Backend: Uses RFC 9457 `ProblemDetails` via `GlobalExceptionHandler` and `Result` pattern. Structured errors are properly handled (e.g., status codes, error details).
- Frontend: Shows `SnackBar` natively. Often relies on raw error messages from backend responses (e.g. `e.response?.data?['message']`) or generic strings like "An unexpected issue occurred. Please check your connection."
- Missing: 
  - "Empathetic" tone (many strings say "Failed to...").
  - "Way out" (SnackBars usually don't have actionable buttons to retry or contact support).
  - Centralized mapping: Devs reinvent the wheel on every form catch block.

**Architectural Needs:**
- We need a centralized `ErrorHandler` or `UIExceptionMapper` on the frontend that converts HTTP exceptions / Dio exceptions into empathetic user-facing strings and Actionable Widgets (like an action button on a SnackBar).
- The `ux-copywriting` skill mandates: No developer jargon, Blame-Free Error States, and Call-to-Action verbs.

**Blind Spots:**
1. **Snackbar vs Dialog context**: A global snackbar might disappear too quickly to offer a "way out" for complex errors. We might need contextual error widgets or Dialogs for critical failures.
2. **Translation/Localization**: Hardcoding empathetic strings requires a centralized dictionary to avoid scattered text, especially if i18n is planned.
3. **Actionability**: A "Retry" button on a SnackBar requires access to the callback that failed. Designing a universal error handler that accepts retry callbacks is slightly more complex.

**Rule Conflicts:**
- The `ux-copywriting` skill STRICTLY forbids jargon and blame. If we use `e.response?.data?['message']` directly on the frontend, we risk displaying backend jargon. The UI must map error codes to safe strings, not blindly render backend text, violating the strict copywriting rules.
</latent_space_scratchpad>

## E2E Workflow Map

1. **Failure Trigger**
   Backend API returns `400 Bad Request` or `500 Internal Error` with `ProblemDetails` JSON.
2. **Interceptor / API Client**
   Flutter `AdminApiService` throws a `DioException` containing the response.
3. **Catch Block (Current vs Target)**
   - *Current*: Local widget catches it, displays a generic or backend-provided string.
   - *Target*: Local widget catches it, passes exception + optional retry callback to a centralized `ErrorDisplayService`.
4. **UX Rendering**
   `ErrorDisplayService` evaluates the error type, looks up an empathetic string from an `ErrorDictionary`, and renders a `SnackBar` with an actionable `Retry` or `Dismiss` button.

### Context Handoff Points
- Backend (`ProblemDetails`) -> Frontend API Service (`DioException`).
- Frontend Widget -> `ErrorDisplayService` (translation from technical to empathetic).
- Error UI -> User Action (the "Way Out").

## Impact Spectrum

| Option | Approach | Pros | Cons |
|---|---|---|---|
| **(A) Strict Native Fit (Central Error Service)** | Create a centralized `ErrorDisplayService` that maps HTTP codes / custom error codes to empathetic UI strings with actionable callbacks. | Guarantees consistent tone. Enforces `ux-copywriting` rules natively. | Refactor required across all API catch blocks. |
| **(B) Pragmatic Balance (Local String Overrides)** | Provide a set of string constants, but allow developers to implement Snackbars manually in each widget. | Lower upfront refactor cost. | Inconsistent UX. Developers will inevitably forget to add the "way out" action button. |
| **(C) Enterprise Textbook Overhaul (Backend Driven UX)** | Backend `ProblemDetails` includes pre-translated, empathetic user-facing title, description, and action intent. | Frontend becomes completely dumb. | Mixes presentation logic (UX copy) into backend domain layer, violating clean architecture. |
