### SA-1 🔴 Fatal — Idempotency Key IDOR

**File:** `server/Features/Submissions/CreateSubmission.cs` — Lines 99–114

**Failure Scenario:**

```
Attacker (Auditor A) submits POST /submissions with X-Idempotency-Key = "abc123"
Auditor A's audit is stored. Key "abc123" is in Postgres.

Auditor B knows (or guesses via brute-force) that "abc123" is a valid key.
Auditor B sends POST /submissions with body { ..., "idempotencyKey": "abc123" }

Server executes:
  var existing = await db.Submissions
      .FirstOrDefaultAsync(s => s.IdempotencyKey == "abc123")
  // existing is NOT null — returns Auditor A's SubmissionDto to Auditor B.
```

**Actual Code:**
```csharp
// Lines 99-114 — NO caller ownership check:
var existing = await db.Submissions
    .AsNoTracking()
    .FirstOrDefaultAsync(s => s.IdempotencyKey == request.IdempotencyKey, ct);

if (existing is not null)
{
    return TypedResults.Ok(new SubmissionDto(...)); // ← Returns ANY match to ANY caller
}
```

**The key is a UUID generated by the Flutter client (`uuid` package, v4). With 122 bits of entropy, brute-force is not viable. BUT:** The idempotency key is embedded in the SQLite `pending_submissions` row. Any actor with access to a stolen device SQLite file gets every key. Moreover, an insider (employee) who exports their own keys and re-sends them against a colleague's store gets valid read access.

**Business Impact:** Full submission DTO disclosure including `StoreName`, `AuditorName`, `TotalScore`, `SectionScores`, `Notes`. Data leak of audit results across store boundaries.

**Fix — Add caller ownership assertion:**
```csharp
if (existing is not null)
{
    // SA-1: Idempotency match must belong to the calling user.
    // Prevents any authenticated user from reading another user's submission via key collision.
    if (existing.AuditorId != callerId)
        return TypedResults.Conflict(new { error = "Idempotency key belongs to a different caller." });

    return TypedResults.Ok(new SubmissionDto(...));
}
```

> **Complexity:** Low — a one-line `if` inserted before the `TypedResults.Ok` return. No schema change, no migration, no test infrastructure change.

> **Trade-offs:**
> - **Pro:** Closes a real IDOR data leak. The check is O(1) — `callerId` is already parsed from the JWT claim on line 35.
> - **Con:** A caller who legitimately submits the same audit from two devices under the same account will be correctly served. The check uses `AuditorId`, which is the caller or a delegated auditor. If `AssignToAuditorId` is used, the key was generated by the caller (not the delegate) — this is still safe because the key was created under the caller's session.
> - **Decision:** **Apply immediately. This is a 1-line fix for a real data exposure.**

### SA-2 🟡 Brittle — Connectivity Stream Zombie

**File:** `lib/_shared/services/sync_engine.dart` — Lines 52–61

**Failure Scenario:**

```
1. App starts. SyncEngine subscribes to _connectivity.onConnectivityChanged.
2. Device is online. SyncEngine.state = idle.
3. OS battery optimization kills the connectivity_plus plugin's native receiver.
   OR: connectivity_plus plugin stream closes due to a platform exception.
4. _connectivitySub receives no more events.
5. User loses WiFi briefly. SyncEngine does NOT see the "offline" event.
6. Next sync cycle: HTTP calls fail with SocketException.
7. SyncEngine.state = error. Retries apply exponential backoff.
8. Device regains WiFi. Plugin stream is dead. SyncEngine NEVER sees "online" event.
9. SyncEngine.state stays = error. Retry timer fires but _connectivity.isOnline
   is stale (plugin not updating it either).
10. User must force-kill and restart the app.
```

**Actual Code:**
```dart
// Lines 52-61: single subscription, never health-checked:
_connectivitySub = _connectivity.onConnectivityChanged.listen((isOnline) {
  if (isOnline) {
    _state = SyncState.idle;
    requestSync();
  } else {
    _state = SyncState.offline;
  }
});
// No onError handler. No onDone handler. No watchdog.
```

The subscription has **no `onError` callback** and **no `onDone` callback**. When the stream closes, the engine silently stops responding to connectivity events. The `_retryTimer` will still fire, but if `_connectivity.isOnline` is also stale (because the plugin is frozen), `_requestSyncInternal()` will see `!isOnline` and immediately set `state=offline` forever.

**Fix — Add stream health guard:**
```dart
_connectivitySub = _connectivity.onConnectivityChanged.listen(
  (isOnline) {
    if (isOnline) {
      _state = SyncState.idle;
      requestSync();
    } else {
      _state = SyncState.offline;
    }
  },
  onError: (Object error) {
    // Stream emitted an error. Log and attempt to recover.
    // The subscription is still alive after onError unless cancelOnError=true.
    debugPrint('[SyncEngine] connectivity stream error: $error');
  },
  onDone: () {
    // Stream closed permanently (plugin restart, OS kill).
    // Schedule a periodic poll fallback so the engine is not permanently frozen.
    debugPrint('[SyncEngine] connectivity stream closed. Activating poll fallback.');
    _startConnectivityPollFallback();
  },
);

// Fallback: poll connectivity every 30s when stream is dead.
void _startConnectivityPollFallback() {
  _retryTimer?.cancel();
  _retryTimer = Timer.periodic(const Duration(seconds: 30), (_) async {
    final isOnline = _connectivity.isOnline;
    if (isOnline && _state != SyncState.syncing) {
      _state = SyncState.idle;
      requestSync();
    }
  });
}
```

> **Complexity:** Medium — requires adding 2 new methods and updating the `listen` call. The `ConnectivityService` interface may need an `isOnline` getter if not already exposed (it is — line 47 shows `_connectivity.isOnline` is already used).

> **Trade-offs:**
> - **Pro:** Device never stays permanently frozen in offline state after a plugin hiccup. The 30-second poll is low-cost (no network I/O — just checks a cached native value).
> - **Con:** The poll adds a permanent `Timer.periodic` callback. If `dispose()` is called without cancelling `_retryTimer`, it leaks. Requires ensuring `dispose()` cancels both subscriptions.
> - **Decision:** Yield to user. This is a resilience hardening, not a correctness bug. Recommended for any deployment with aggressive battery optimization (most Android OEMs in Southeast Asia).

### SA-3 🟡 Brittle — Clock Drift Cursor Corruption

**File:** `lib/_shared/services/sync_api_adapter.dart` — Lines 125–133

**Failure Scenario:**

```
Device clock is 5 minutes in the future (common on Android without NTP sync).

1. First sync: cursorUpdatedAt = null → server returns everything up to now.
2. Last item has server-side updated_at = "2026-05-20T14:00:00Z".
3. Client parses lastItem['updatedAt'] and sets cursor = "2026-05-20T14:00:00Z".
4. Next sync: GET /sync/submissions?cursorUpdatedAt=2026-05-20T14:00:00Z
5. Server returns records WHERE updated_at > "2026-05-20T14:00:00Z".
6. In the 5-minute gap (14:00–14:05), 10 new submissions were created by other users.
   These are NOT returned — client cursor jumped past them.
7. Client never sees these records until a full resync (e.g., logout/login).
```

BUT: The cursor is the **server's `updated_at` timestamp from the last returned item** — not the device clock. So the immediate gap only occurs if the server and client clocks drift. The real risk is **cursor fallback on empty response** (line 125):

```dart
DateTime nextTimestamp = cursorUpdatedAt ?? DateTime.now();  // ← Device clock used as fallback!
if (items.isNotEmpty) {
  final lastItem = items.last as Map<String, dynamic>;
  if (lastItem['updatedAt'] != null) {
    nextTimestamp = DateTime.parse(lastItem['updatedAt'] as String);
  }
}
```

If the response is empty (no new records), `nextTimestamp` stays as `cursorUpdatedAt`. Fine. But if `cursorUpdatedAt == null` **and** items is empty (first sync with no data), `nextTimestamp = DateTime.now()` — the **device's local clock**. On a device 3 years in the future, the cursor is set to 2029, and from now on every delta pull returns zero records permanently.

**Fix — Use the server's timestamp, never the device clock:**
```dart
// In pullDeltas, the server should return a serverTimestamp even when items is empty.
// Fix: require the backend to include a `serverTimestamp` field in DeltaPullResult.

// Backend: add to the sync endpoint response:
// { "items": [], "hasNextPage": false, "serverTimestamp": "2026-05-20T14:00:00Z" }

// Client: prefer serverTimestamp, never fall back to DateTime.now():
final serverTs = data['serverTimestamp'] as String?;
DateTime nextTimestamp = serverTs != null
    ? DateTime.parse(serverTs)
    : (cursorUpdatedAt ?? DateTime.utc(2020)); // Safe floor, not device clock
```

> **Complexity:** Medium — requires a backend change (add `serverTimestamp` to the sync endpoint response DTO) + a client change (parse and prefer it). The server gets its timestamp from `DateTimeOffset.UtcNow` at the start of the sync query — authoritative.

> **Trade-offs:**
> - **Pro:** Eliminates device-clock dependency for the sync cursor. Server clock is the single source of truth.
> - **Con:** Backend API contract change — requires a migration step. Old clients (without the fix) continue to use device clock until they update.
> - **Decision:** Yield to user. The risk is low for correctly time-synced devices (most modern phones with NTP). High risk for offline-first field devices in deployments where NTP is unavailable (e.g., stores with no internet for days).

### SA-4 🟡 Brittle — Thundering Herd on Reconnect (Delta Pull + Submission Push)

**File:** `lib/_shared/services/photo_queue_service.dart:59` (jitter only for photos)
**File:** `lib/_shared/services/sync_module.dart` (no jitter in executePull/executePush)

**Failure Scenario:**

```
50 auditors are doing in-store audits. Store WiFi goes down for 10 minutes.
At T+10min, WiFi restores.

All 50 SyncEngines fire onConnectivityChanged at the same millisecond.
All 50 call requestSync() simultaneously.

Phase 1 (Pull):
  50 × GET /sync/submissions → 50 simultaneous Postgres queries
  Server renders 50 full delta queries under N seconds of load

Phase 2 (Push):
  50 × POST /submissions → 50 simultaneous EF Core insert transactions
  50 × INSERT INTO submissions (+ answers, + action_plans, + outbox_messages)
  Postgres connection pool exhausted → timeout exceptions → retry storm begins

The photo jitter (0-15 seconds) does NOT apply here.
The first 2 sync phases (pull + submission push) hit the server at T=0 with no delay.
```

**Fix — Add pre-sync jitter to `SyncEngine.requestSync()` for reconnect events:**
```dart
// In _connectivitySub listener, add a reconnect jitter:
_connectivitySub = _connectivity.onConnectivityChanged.listen((isOnline) {
  if (isOnline) {
    _state = SyncState.idle;
    // Add 0-10 second jitter to stagger reconnect storms.
    final jitterMs = Random().nextInt(10000);
    Future.delayed(Duration(milliseconds: jitterMs), requestSync);
  } else {
    _state = SyncState.offline;
  }
});
```

OR, alternatively, implement server-side rate limiting per client IP on the sync endpoint.

> **Complexity:** Low (client jitter) — one `Future.delayed` wrapper. Medium (server rate limiting) — requires adding `AspNetCoreRateLimiting` middleware to the sync endpoint.

> **Trade-offs:**
> - **Client jitter Pro:** Zero server changes. Immediately reduces peak load.
> - **Client jitter Con:** Adds up to 10 seconds of sync delay on reconnect. On a fast WiFi reconnect, users may notice their data is stale for longer.
> - **Server rate limit Pro:** Canonical solution — protects the server regardless of client behavior. Handles misconfigured / patched clients.
> - **Server rate limit Con:** Requires adding `AddRateLimiter` to `Program.cs`. Must tune window/permit counts carefully to avoid blocking legitimate bursts.
> - **Decision:** Yield to user. Client jitter is the fastest fix. Server rate limit is the production-grade solution. Recommend both for large-scale deployments (>20 concurrent users).

### SA-5 🟡 Brittle — Outbox Polly Burn on 400 Storm

**File:** `server/Common/Services/OutboxBackgroundService.cs` — Lines 89–104

**Failure Scenario:**

```
A malformed `Notification` outbox message is written with invalid JSON payload.
(e.g., missing "UserId" field, or "UserId" is not a valid GUID)

Poll cycle picks up 50 messages. Message #1 is malformed.

_retryPipeline.ExecuteAsync():
  Attempt 1: JsonDocument.Parse fails → Exception thrown
  Polly waits 2s... retry
  Attempt 2: same failure
  Polly waits 4s... retry
  Attempt 3: same failure
  Polly waits 8s... retry
  Attempt 4: throws → caught by outer catch → message.Error written.

Total time blocked on message #1 alone: 2+4+8 = 14 seconds.
If all 50 messages are malformed: 50 × 14 = 700 seconds (11.6 minutes) per poll cycle.
During this time, NO valid messages are processed.

(Note: in practice, malformed payloads come in bursts when a bug ships.
 A deploy with a broken FCM payload serializer would cause this exact scenario.)
```

**Root Cause:** Polly retries ALL exceptions with the same policy, including `JsonException` and `GuidParseException` — which are deterministic (400-class) failures that will never succeed on retry.

**Fix — Classify exceptions before applying retry:**
```csharp
private static bool IsFatalMessageError(Exception ex) =>
    ex is JsonException ||
    ex is FormatException ||   // Invalid GUID
    ex is ArgumentException;   // Null/empty payload

// In the retry pipeline:
private readonly ResiliencePipeline _retryPipeline = new ResiliencePipelineBuilder()
    .AddRetry(new RetryStrategyOptions
    {
        MaxRetryAttempts = 3,
        BackoffType = DelayBackoffType.Exponential,
        Delay = TimeSpan.FromSeconds(2),
        // ONLY retry transient exceptions — not deterministic parse/format failures:
        ShouldHandle = new PredicateBuilder()
            .Handle<Exception>(ex => !IsFatalMessageError(ex)),
        OnRetry = args =>
        {
            logger.LogWarning(args.Outcome.Exception, "Error processing outbox message. Retrying...");
            return ValueTask.CompletedTask;
        }
    })
    .Build();
```

> **Complexity:** Low — adding a `ShouldHandle` predicate to the existing `RetryStrategyOptions`. The `IsFatalMessageError` helper is a 5-line static method.

> **Trade-offs:**
> - **Pro:** Deterministic failures (bad JSON, invalid GUID) skip all 3 retries and immediately write `Error`. Poll cycle processes message #2 in under 100ms instead of 14 seconds.
> - **Con:** If `JsonException` is thrown by a transient I/O error (unlikely but possible for very large payloads), it will be classified as fatal and not retried. In practice, Polly is already configured for `Handle<Exception>()` which catches `JsonException` — the new predicate is strictly more discriminating.
> - **Decision:** Apply immediately. This is a resilience hardening with no functional behavior change for correctly-formed messages.

### SA-6 🟢 Optimization — `syncableCount()` Runs 3 Sequential DB Queries

**File:** `lib/_shared/database/dao/outbox_dao.dart` — Lines 268–283

**Problem:** The count check runs 3 separate DB queries in a for-loop:
```dart
for (final status in ['pending', 'submission_synced', 'photos_pending']) {
  // 3 × SELECT COUNT(*) FROM pending_submissions WHERE sync_status = ?
}
```

**Fix — Single query with `IN`:**
```dart
Future<int> syncableCount() async {
  const recoverableStatuses = ['pending', 'submission_synced', 'photos_pending'];
  final countExp = countAll();
  final query = _db.selectOnly(_db.pendingSubmissions)
    ..addColumns([countExp])
    ..where(_db.pendingSubmissions.syncStatus.isIn(recoverableStatuses));
  return await query.map((row) => row.read(countExp)).getSingle() ?? 0;
}
```

> **Complexity:** Low — replaces 3-loop with a single `isIn()` Drift query.

> **Trade-offs:** Pro: 3× faster. Con: None. The result is identical.
