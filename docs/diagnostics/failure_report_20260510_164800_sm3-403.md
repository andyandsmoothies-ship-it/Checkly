# Diagnostic Report: Store Manager 403 on FinalizeSubmission

## Input Lineage
- **Source Log Input**: `HTTP PUT /api/submissions/1ab58e3f-fd86-4b3a-96da-2e0f54aeb140/finalize responded 403`

## Root Cause
There were two logical bugs preventing Store Managers from completing scheduled audits created by Admins/Area Managers:
1. **The Claiming Bug (UpdateSubmission.cs)**: When an admin schedules an audit, `CreateSubmission` correctly defaults `AuditorId` to the Admin's ID. However, when the Store Manager started the audit (transitioning it to `draft`), `UpdateSubmission.cs` had a guard `if (!submission.AuditorId.HasValue)` before updating the `AuditorId`. Because the `AuditorId` *did* have a value (the Admin's ID), the Store Manager never officially claimed ownership of the draft in the database.
2. **The Finalize Bug (ResourceAccessGuard.cs)**: When the Store Manager attempts to finalize the audit, `FinalizeSubmission.cs` verifies if the user is the `AuditorId`. Since they weren't (due to Bug 1), it falls back to `ResourceAccessGuard.CanDelegateAsync`. This guard historically only permitted Admins and Area Managers to manipulate resources on behalf of other users, instantly returning `false` for Store Managers. 

These combined to block the Store Manager with a `403 Forbidden` despite it being their own store's scheduled audit.

## Explicit Code Trace (Premises + Proof)
- **Premise 1**: The user reported they could "start an audit" but not submit it.
- **Premise 2**: `UpdateSubmission.cs` lines 61-65 blocked overwriting the `AuditorId` if it already had a value.
- **Premise 3**: `FinalizeSubmission.cs` calls `CanDelegateAsync` if the user's ID does not match the `AuditorId`.
- **Premise 4**: `ResourceAccessGuard.CanDelegateAsync` explicitly returned `false` for the `store_manager` role.
- **Proof**: A trace of the code confirmed that a `store_manager` finalizing a submission assigned to an admin triggers the `return TypedResults.Forbid();` condition exactly as seen in the logs.

## Proposed Scope-Limited Fix
- **Fix 1 (Data Integrity)**: Update `UpdateSubmission.cs` to explicitly overwrite `submission.AuditorId = callerId;` unconditionally when a scheduled audit is started. This guarantees the person actually performing the audit is held accountable.
- **Fix 2 (Workflow Resilience)**: Update `ResourceAccessGuard.CanDelegateAsync` to permit the `store_manager` role to delegate/finalize resources, provided those resources are explicitly bound to their assigned store via `IsUserStoreAsync`. This immediately unblocks any existing "stuck" drafts on users' devices.

**Trade-offs / Pros & Cons**:
- **Pros**: Resolves the sync error instantly for all in-flight and future scheduled audits without data loss. Ensures accurate accountability (the actual auditor's ID is recorded). Aligns PBAC correctly for retail Store Managers.
- **Cons**: Store Managers can now theoretically modify draft audits assigned to other users *within their own store*. This is an acceptable (and often desired) trade-off in retail environments to prevent audits from locking if a specific supervisor is sick.
