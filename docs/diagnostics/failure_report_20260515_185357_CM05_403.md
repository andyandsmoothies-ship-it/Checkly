# Diagnostic Report: Area Manager 403 on /programs/area-progress

## Input Lineage
- Source Input: `GET /programs/area-progress` returned 403 (Forbidden) for Area Manager.

## Root Cause
The `Area Manager` role was not granted the `programs:assignments_list` capability in the database seed. The `GET /api/programs/area-progress` endpoint in `ProgramEndpoints.cs` requires this capability to allow access. Since the capability was only seeded for the `admin` role, area managers received a `403 Forbidden` despite being authenticated.

## Explicit Code Trace (Premises + Proof)
1. In `ProgramEndpoints.cs`, `group.MapGet("/area-progress", GetAreaCampaignProgress.HandleAsync)` applies `.RequireCapability(AppCapabilities.ProgramsAssignmentsList)`.
2. In `Program.cs`, the database initialization explicitly inserted `(gen_random_uuid(), 'admin', 'programs:assignments_list', now())` but omitted `area_manager`.
3. In `TestWebApplicationFactory.cs`, the integration test seed also omitted `area_manager`.
4. Therefore, when an `area_manager` logged in and accessed the dashboard, the JWT contained PBAC capabilities that lacked `programs:assignments_list`, causing the authorization middleware to reject the request with a 403.

## Proposed Scope-Limited Fix
**Trade-offs / Pros & Cons:**
The fix is to seed the `programs:assignments_list` capability for the `area_manager` role in both `Program.cs` and `TestWebApplicationFactory.cs`.
- **Pros:** Directly unblocks the Area Manager dashboard functionality. Adheres to the PBAC strategy of explicitly granting capabilities to roles in the bootstrap script.
- **Cons:** This grants the `area_manager` the capability `programs:assignments_list`. However, we have already ensured inside the `GetAreaCampaignProgress.cs` handler that data access is safely scoped to `ProfileStoreAssignments`, preventing the area manager from querying data outside their authorized stores. So this capability elevation is completely safe.
