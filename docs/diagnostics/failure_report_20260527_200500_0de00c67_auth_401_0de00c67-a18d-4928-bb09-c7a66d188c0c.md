Workflow: /diagnose | Track: B1

## 1. System Design Pattern
This is a classic **Stale Token / Blind-Trust Auto-Login Recovery Flow**. 

Instead of validating the stored authentication token against the backend *before* changing the authentication state, the frontend practices "Optimistic Auto-Login" (blindly trusting the stored credentials). When the token is rejected by the backend, a cascade of concurrent requests all fail with `401 Unauthorized` before the global interceptor can clear the session and redirect the user back to the Login UI.

## 3. Root Cause Analysis

### The Premises & Evidence
1. **The Backend is Healthy**: Connecting and executing `curl http://localhost:5288/health` returns `Healthy`.
2. **401 Response received**: The backend returned a status code of `401 Unauthorized` for all authenticated endpoints. This means the request successfully reached the server, but the server rejected the credentials.
3. **The Token is Stale or Expired**: 
   - *Reason A*: In local development environments, the PostgreSQL database is often reset, re-migrated, or reseeded. Any active tokens issued *before* the database reset refer to user records or encryption keys that no longer exist or are invalid.
   - *Reason B*: The JWT token has reached its 24-hour lifetime expiration limit, and the backend has rejected it.

### Current Mitigation Behavior (It Works!)
The Flutter app has a global `Dio` interceptor in [api_client.dart](file:///c:/Users/HP/Documents/GitHub/Checkly/lib/_shared/services/api_client.dart):
```dart
if (error.response?.statusCode == 401) {
  final path = error.requestOptions.path;
  if (!path.contains('/auth/login') && !path.contains('/auth/register')) {
    try {
      di<AuthManager>().logout();
    } catch (e) {
      debugPrint('[API] Failed to auto-logout on 401: $e');
    }
  }
}
```
When the first `401` error occurs, the interceptor correctly triggers `logout()`, which wipes the invalid token and safely redirects the user to the Login screen. The other logs are simply the remaining concurrent requests finishing their execution after the token was already recognized as invalid.

---

## 4. Pros & Cons of Solutions

We have two options to manage this console noise:

### Option A: Let the Stale Token Flow Recover (Do Nothing / Recommended)
*   **Pros**: Zero code complexity. The current system is secure, self-healing, and correctly wipes local caches and redirects the user to the Login UI when a token expires.
*   **Cons**: Shows some 401 console noise during initial startup if a user has a stale token.
*   **Verdict**: This is normal, healthy offline-first token recovery behavior.

### Option B: Validate Token Before Allowing Concurrent Requests
*   **Pros**: Eliminates console noise on startup by checking token validity first.
*   **Cons**: Increases app startup time by requiring a blocking round-trip network call before loading the main screens. If the user is offline, this blocking check would fail or timeout, degrading the offline-first experience.
