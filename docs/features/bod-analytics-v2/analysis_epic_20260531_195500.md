<latent_space_scratchpad>
Pattern: **Role-Scoped Read API** (Projection Pattern). There is no state machine here. No new entities. The core is: "same data, different filter lens per role."

Key insight from codebase exploration:
- `GetBodReport.cs` today only serves Admin (global view). It supports province/district filter via query params for live mode. It reads from `BodReportSnapshot` (pre-computed nightly JSONB cache).
- `GetStoreBodSummary.cs` already gives a store-level section breakdown. But it lacks: peer comparison (quartile), regional avg score, SLA bucket data.
- `SubmissionSectionScores` table already has `SectionTitle`, `StoreId`, `Score`, `MaxScore`. This is the gold mine for section analytics.
- `ActionPlan` has `DueDate`, `ClosedAt`, `StoreId`. SLA buckets (0-7d, 8-30d, 31+d) need a computed `DaysOverdue` projection.
- Tenancy: `ProfileStoreAssignment` links `ProfileId` → `StoreId` (1-to-1 unique per the global gotcha). To scope an Area Manager's data, we join `ProfileStoreAssignments` WHERE `ProfileId = currentUserId`.
- `AppCapabilities.AnalyticsArea` is already reserved (noted in comment line 13 of AppCapabilities.cs) for a future Slice 2 migration. This confirms the exact planned path.

Shape A: Extend existing GetBodReport with role-based branching
- Detect role from JWT claims inside `GetBodReport.cs`
- Branch to AM/SM data sub-queries within the same handler
- Pros: fewer files, one endpoint
- Cons: one handler grows to 500+ lines (violates 400-line rule), role branching is untestable, violates SRP

Shape B: Three separate endpoint handlers (CHOSEN)
- `GET /api/analytics/bod` — Admin global (EXISTING)
- `GET /api/analytics/bod/area` — Area Manager scoped (NEW, capability: `analytics:area`)
- Extend existing `GET /api/analytics/stores/{storeId}/bod-summary` — Store Manager scoped (EXTEND existing endpoint)
- Pros: clean SRP, each handler tests independently, follows existing project style exactly, no role if/else chains
- Cons: a few shared helpers may be needed (SLA bucket query)

Decision: **Shape B**

Key Risk: The `AppCapabilities.AnalyticsArea` constant is already declared but not yet seeded (comment says "reserved for Slice 2"). When we add this capability, we MUST seed it in `Program.cs` AND `TestWebApplicationFactory.cs` (The 7 Sync Steps rule).
</latent_space_scratchpad>

## Risk Review & Security

- **DB Architect (9/10)**: No N+1. AM query uses single `JOIN ProfileStoreAssignments → Submissions → SectionScores`. Regional avg reuses `ProvinceBenchmarkSnapshots` if available.
- **Security Auditor (9/10)**: AM endpoint enforces `AnalyticsArea` capability. SM endpoint must verify that the `storeId` in the URL matches the SM's own `Profile.StoreId` (or they have `AnalyticsBod`). IDOR risk: any user with the URL can request any store summary — must add tenancy guard.
- **Junior Dev (9/10)**: Clear SRP per handler. Shared SLA bucket query extracted to a private static method. New `AreaBodResponse` DTO is self-documenting.

**Security Fix Required (CATCH-FLOPS AUDIT 2026-05-31)**:
1. **Critical IDOR Guard**: `GetStoreBodSummary.cs` currently has no tenancy check — any authenticated user can request any store. We MUST add a role-scoped tenancy check:
   - Admin → unrestricted access.
   - Auditor → 403 Forbidden.
   - Store Manager → restricted to their assigned store (`profile.StoreId == storeId`).
   - Area Manager → restricted to stores assigned via `ProfileStoreAssignments`.
2. **Missing Constant Fix**: We MUST define the missing `AnalyticsArea` constant in `AppCapabilities.cs` to prevent magic string usage.
