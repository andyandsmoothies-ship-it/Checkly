## Latent Space Scratchpad

### High-Impact DB Schema Optimization (Slice 2)
Slice 2 focuses strictly on optimizing the database queries for the live analytics path by adding highly tailored composite indexes. 

Let's verify the EXACT composite index column order and why:
1. **submissions: (status, completed_at DESC)**
   - Used by: Almost all BOD KPIs (e.g., totalAudits, avgScore, geofenceBypassCount) and top/bottom leaderboard queries.
   - Filter criteria: `s.Status == "completed" && (s.CompletedAt ?? s.CreatedAt) >= start30DaysAgo`
   - In Slice 3, we will rewrite `(s.CompletedAt ?? s.CreatedAt)` to use `s.CompletedAt.Value >= ...`.
   - Index layout: `(status, completed_at DESC)`. Since PostgreSQL B-tree can scan indices backwards, `(status, completed_at)` works, but specifying `IsDescending(false, true)` matches our query ORDER BY/sorting expectations perfectly.
   - Why: Equality filter `status = 'completed'` followed by range filter `completed_at >= start30DaysAgo`. Placing `status` first ensures high cardinality filtering, then range scan on `completed_at`.

2. **submissions: (status, store_id, completed_at)**
   - Used by: Leaderboard aggregation: `g.GroupBy(s => s.StoreId)`.
   - Why: Speeds up GROUP BY and filters on `status` and `completed_at` when store list is fetched.

3. **submission_section_scores: (created_at, store_id)**
   - Used by: Category weaknesses aggregation.
   - Filter criteria: `ss.CreatedAt >= start90DaysAgo && ss.StoreId.HasValue`.
   - Why: Filters out scores older than 90 days first, then allows index cover/lookup on `store_id` for aggregation.

4. **action_plans: (status, deadline)**
   - Used by: Overdue action plans count KPI.
   - Filter criteria: `ap.Status == "open" && ap.Deadline <= now`.
   - Why: Equality filter on `status` first, followed by range scan on `deadline`.

2. **Duplicate Index Names/Collisions**:
   - *Mitigation*: Use unique index names generated by Entity Framework or specify them explicitly (e.g., `IX_submissions_status_completed_at`).
