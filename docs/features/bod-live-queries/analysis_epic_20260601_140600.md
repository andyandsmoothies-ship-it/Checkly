## My analysis

### What the code does today
`GET /api/analytics/bod` has two paths:
1. If `?province=` is provided → runs **live queries** on DB (lines 31–406), caches result in IMemoryCache for 60s, returns data.
2. If **no filter** → reads from `bod_report_snapshots` table (lines 409–451). The snapshot is written by `BodReportWorker` nightly at 02:00 AM.

### What we need to do for Solution B
- Delete the nightly worker entirely (`BodReportWorker.cs`)
- Delete the snapshot infrastructure (`BodReportSnapshot` entity, `BodReportSnapshotConfiguration`, migration)
- Make the global (no-filter) dashboard path run the SAME live queries as the province-filtered path
- Add targeted composite indexes to make the queries fast at scale

### Key queries in GetBodReport.cs (live path)
1. **KPIs**: `submissions` filtered by `status='completed'`, `completed_at >= now-30d`, `store_id IN (filtered)` — GROUP BY to get count/avg
2. **Store Leaderboard**: same filter + GROUP BY `store_id` → ORDER BY avg DESC/ASC
3. **Trend**: `submissions` filtered by `completed_at >= now-12months` GROUP BY year/month
4. **Weaknesses**: `submission_section_scores` filtered by `created_at >= now-90d`
5. **Action Plan Aging**: `action_plans` filtered by `status='open'`
6. **Auditor Productivity**: `submissions` filtered by `completed_at >= now-30d` GROUP BY auditor_id

### Missing indexes for global (unfiltered) path
Currently the live query path was designed for **province-filtered** (small dataset). For the global path (ALL stores), we need:
- `submissions`: composite index on `(status, completed_at DESC)` — the most critical, filters 90% of rows
- `submissions`: composite index on `(status, store_id, completed_at)` — for leaderboard group by store
- `submission_section_scores`: composite index on `(created_at, store_id)` — for weakness aggregation
- `action_plans`: `(status, store_id)` already exists. Need `(status, deadline)` for overdue count.

## Executive Summary

**Pattern**: Query Aggregation over Indexed Read Model

The BOD Analytics dashboard currently has two code paths:
1. **Filtered path** (province/district): already runs live SQL queries on every request.
2. **Global path** (no filter): reads a pre-computed JSON blob from `bod_report_snapshots` — written once per night by `BodReportWorker`.

**Solution B eliminates the snapshot architecture entirely.**

The global dashboard path will run the same live queries as the filtered path, backed by new composite database indexes to keep response times fast at scale. The nightly background worker, the snapshot entity, its EF configuration, and the DB migration are all deleted. The `/bod/refresh` endpoint becomes meaningless and is also deleted.
